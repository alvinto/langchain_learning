# 长时间应用开发里的 Harness 设计

> 基于 Anthropic Engineering 博客《Harness design for long-running application development》的中文改写示例。
> 原文：https://www.anthropic.com/engineering/harness-design-long-running-apps
> 发布时间：2026-03-24

过去几个月，Anthropic Labs 团队在两个看起来不同、但底层很相似的问题上做实验：一个是让 Claude 生成更高质量的前端设计，另一个是让它能长时间自主构建完整应用。结论很明确：真正拉开差距的不是单次模型调用，而是模型外面那一层 **Harness**。

Harness 可以理解为包住模型的运行系统：它决定谁负责规划、谁负责生成、谁负责评价，任务如何拆分，反馈如何进入下一轮，什么时候继续、什么时候停下。对于长时间的软件开发任务，Harness 的设计质量直接决定最终应用能不能从“看起来像个 demo”变成“真的能用”。

## 朴素 Agent 为什么会失败

最简单的 Agent 实现通常是一个循环：模型看上下文、调用工具、得到结果、继续下一步。这个版本能跑 demo，但做长时间任务时很容易掉线。

第一个问题是上下文退化。任务越长，模型越容易丢失整体目标，或者在接近上下文上限时过早收尾。早期方案会使用 context reset：清空上下文，重新启动一个 Agent，同时通过结构化交接文档把当前状态和下一步传给它。这样能给模型一个干净窗口，但代价是系统复杂度、token 开销和延迟都会上升。

第二个问题是自我评价不可靠。让生成者评价自己的作品，往往会得到过于乐观的结论。前端设计尤其明显：模型可能觉得页面“已经很好”，但人类一看就知道它只是安全、普通、模板化。即使在有测试的软件任务里，模型也可能低估交互缺陷、功能缺口和产品体验问题。

所以核心思路变成：**把做事的 Agent 和评价的 Agent 分开**。生成者负责产出，评价者负责挑刺。评价者本身也需要调教，但调教一个独立评价者，比让生成者对自己保持严格要容易得多。

## 前端设计：把主观审美变成可评分标准

Anthropic 先在前端设计上验证这个思路。设计质量很难用一个绝对分数衡量，但可以拆成更具体的评价维度。

实验里使用了四类标准：

- **设计质量**：页面是否像一个整体，而不是零散组件拼起来
- **原创性**：有没有具体的视觉决策，还是库默认样式和常见 AI 模板
- **工艺执行**：字体层级、间距、色彩、对比度是否稳定
- **功能可用性**：用户是否能理解页面并完成关键动作

其中最重要的是设计质量和原创性。模型默认就能做到“基本可用”，但容易产出过于泛化的设计。评价标准明确惩罚模板化布局、过度安全的白卡片、常见紫色渐变等 AI 生成痕迹，会迫使生成者做更有方向感的视觉尝试。

这个前端 Harness 使用 generator-evaluator 循环：生成 Agent 先根据提示词做一个 HTML/CSS/JS 页面；评价 Agent 通过 Playwright MCP 打开页面、点击、截图、观察，再按标准打分并写反馈。反馈再交回生成 Agent，进入下一轮迭代。

每次生成会跑 5 到 15 轮。随着评价反馈进入循环，作品通常会变得更有风格。有时是逐步打磨，有时是突然转向。一个有意思的现象是，评价标准里的措辞会反过来塑造最终风格：如果标准强调“博物馆级设计”，模型会逐渐朝某种更强烈、更沉浸的视觉语言靠拢。

## 扩展到全栈应用开发

前端实验验证了一个模式：生成者和评价者分离，可以让模型从外部反馈中进步。接下来，这个模式被扩展到全栈应用开发。

新的 Harness 变成三类 Agent：

1. **Planner**：把用户一两句话的需求扩展成完整产品规格。它不写底层实现细节，而是定义产品目标、范围和高层技术方向。
2. **Generator**：按规格构建应用。它负责实现功能、提交代码、自检当前结果。
3. **Evaluator**：像 QA 一样操作真实应用。它用 Playwright 点击页面、检查 API、验证数据库状态，并按产品深度、功能完整性、视觉设计和代码质量打分。

这里有一个关键机制：每个阶段开始前，Generator 和 Evaluator 会先协商一份 sprint contract，也就是“这一轮到底算完成什么”。Generator 提出要做的功能和验收方式，Evaluator 审核这些标准是否足够具体。只有双方达成一致，Generator 才开始写代码。

这种合同机制解决了一个常见问题：产品规格如果写得太细，错误会传导到后面；如果写得太粗，生成者又容易随意发挥。用 sprint contract 把高层规格转成可验证任务，可以在灵活性和可测试性之间取得平衡。

## 单 Agent 和完整 Harness 的差距

Anthropic 用一个“2D 复古游戏制作器”任务做对比。单 Agent 版本大约跑 20 分钟，完整 Harness 跑了约 6 小时，成本也高得多。但质量差距非常明显。

单 Agent 版本看起来符合预期，但真正操作时问题很快暴露：布局浪费空间，工作流僵硬，用户不知道应该先做精灵还是先放关卡。更严重的是，核心玩法没有跑通，实体显示在画面上，却不能正确响应输入。

完整 Harness 版本从同一句需求出发，Planner 把它扩展成包含 16 个功能、10 个 sprint 的产品规格。除了关卡编辑器、精灵编辑器、行为系统和可玩测试模式，还加入了动画、音效、AI 辅助生成和分享链接等能力。最终应用仍有缺陷，但核心 play mode 可以运行，编辑器也更完整。

真正重要的是 Evaluator 的反馈质量。它不是笼统地说“有 bug”，而是指出具体验收标准没有通过、哪个交互没触发、哪个 API 路由顺序导致请求被错误匹配。这种反馈足够具体，Generator 才能继续修。

## Harness 也需要被简化

完整 Harness 很强，但慢、贵、复杂。下一步不是无脑加 Agent，而是找出哪些组件真的是“承重墙”。

随着模型能力提升，原来必须靠 Harness 补的能力可能会变成模型原生能力。Anthropic 在新一轮实验中移除了 sprint 结构，让构建过程更连续，只保留 Planner 和 Evaluator。结果显示：对于模型已经能稳定完成的部分，Evaluator 的价值下降；但对于仍处在能力边界上的任务，Evaluator 仍然能抓住关键缺口。

这带来一个实用结论：Evaluator 不是固定要不要的问题，而是取决于任务是否超过当前模型的可靠能力边界。

## 一个新的应用例子：浏览器里的 DAW

更新后的 Harness 被用来构建一个浏览器版数字音频工作站。任务是做一个可以编曲、录音和混音的 Web Audio 应用。

这次运行仍然很长，接近 4 小时，成本超过 100 美元。Builder 连续工作了两个多小时，说明更新后的模型已经能在没有 sprint 拆解的情况下保持较长时间的连贯性。

但 QA 仍然抓到了关键问题：应用视觉上完整，AI 集成也能工作，可一些核心 DAW 交互只是展示层，没有真正实现。例如时间线上的 clip 不能拖动，录音按钮只是切换状态，没有实际捕获麦克风，效果器也缺少真正的可视化编辑。

这些不是边角问题，而是决定这个应用能不能被称为 DAW 的核心交互。Evaluator 的价值就在这里：它把“看起来完成了”拆成“哪些关键行为真的可用”。

## 对 Agent 工程的启发

这篇博客最值得记住的不是某个固定架构，而是 Harness 设计的方法论。

第一，复杂任务不要只靠单个生成 Agent。只要任务有主观质量、长时间执行或复杂交互，就要考虑独立评价者。

第二，评价标准要具体。不要问“这个设计好不好”，而要问“视觉是否统一、是否原创、是否可用、是否有明确层级”。不要问“应用完成了吗”，而要让 Evaluator 逐条验证用户故事和关键交互。

第三，Harness 要随着模型变化而变化。模型变强后，某些拆解、重置或中间检查可能不再必要；但也会出现新的上限，值得用新的 Agent 组合去突破。

最终结论是：模型能力提升不会让 Harness 消失。相反，真正有趣的工程工作会不断移动到新的边界上。AI 工程师要做的，是持续观察模型在哪些地方已经可靠，在哪些地方还需要脚手架，然后设计最小但有效的 Harness。
